# 테스팅 가이드

TDD 통합 우선 접근법을 위한 포괄적인 테스팅 가이드입니다.

## TDD 순서

### ❌ 잘못된 순서
1. 헬퍼 함수를 위한 유닛 테스트 작성
2. 헬퍼 구현
3. 나중에 실제 사용에 통합

### ✅ 올바른 순서
1. **RED**: 실제 사용 시나리오를 위한 통합/E2E 테스트 작성
2. **GREEN**: 통합 테스트를 통과시키기 위한 모든 필요한 코드 구현
3. **REFACTOR**: 통합 테스트를 통과시키면서 코드 품질 개선

## 테스트 환경

### 프레임워크
- **백엔드 유닛**: Mocha (ts-node)
- **웹뷰**: Vitest

### 빠른 명령어
| 테스트 유형 | 명령어 |
|------------|--------|
| 백엔드 유닛 | `npm run test:unit` |
| 통합 | `npm run test:integration` |
| 웹뷰 | `npm run test:webview` |
| 타입 체킹 | `npm run check-types` |
| 컴파일 | `npm run compile` |

> 참고: `npm test`는 유닛 + 통합을 실행합니다 (더 느림)

## 테스트 파일 위치

| 테스트 유형 | 위치 |
|------------|------|
| 백엔드 유닛 테스트 | `src/**/__tests__/*.ts`, `careti-src/core/task/tools/__tests__/*.ts` |
| 통합 테스트 | `src/test/**` |
| 웹뷰 테스트 | `webview-ui/src/**` |

> 참고: 저장소의 기존 패턴 준수. `.mocharc.json`이 Mocha glob을 정의합니다.

## TDD 예시

### 웹뷰
- **❌ 잘못됨**: `isValidInput()` 유닛 테스트로 시작
- **✅ 올바름**: "사용자가 버튼 클릭 → 예상 결과 표시" 컴포넌트 테스트로 시작

### 백엔드
- **❌ 잘못됨**: `parseConfig()` 유닛 테스트로 시작
- **✅ 올바름**: "설정 변경 → 시스템 동작 변경" 통합 테스트로 시작

## 테스팅 전략

1. **통합 테스트** - 주요 초점, 실제 사용 시나리오
2. **컴포넌트 테스트** - 사용자 상호작용과 함께하는 React 컴포넌트 동작
3. **유닛 테스트** - 통합 테스트의 부산물, 시작점 아님
4. **E2E 테스트** - Playwright로 전체 워크플로우 검증

## 검증 워크플로우

1. 실패하는 통합 테스트 작성 (RED)
2. 테스트를 실행하여 실패 확인
3. 통과하기 위한 최소 코드 구현 (GREEN)
4. 테스트를 실행하여 성공 확인
5. 회귀 방지를 위해 전체 테스트 스위트 실행
6. 모든 테스트 통과를 유지하면서 리팩토링

## 커버리지 목표

- 새 Caret 기능에 100% 커버리지
- 모든 사용자 대면 기능에 통합 테스트 커버리지
- 모든 UI 상호작용에 컴포넌트 테스트 커버리지

## 일반 패턴

- **모킹**: 외부 의존성을 위한 Vitest 모킹 패턴
- **비동기 테스팅**: 테스트에서 적절한 async/await 처리
- **컴포넌트 테스팅**: React Testing Library 패턴
- **상태 테스팅**: 익스텐션 상태 및 스토리지 테스팅

## 가이드라인

- 개발자와 동일한 테스팅 지식에 AI 접근 제공 (testing-guide.md)
- 항상 실제 사용자 시나리오를 대표하는 통합 테스트로 시작
- 절대 격리된 유닛 테스트로 시작하지 않음
- 목표는 코드가 격리가 아닌 실제 사용 컨텍스트에서 작동하는지 보장
