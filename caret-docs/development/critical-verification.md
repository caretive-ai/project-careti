# 비판적 검증 워크플로우 - 3단계 분석

과도한 비판과 맹목적인 수용을 모두 피하기 위해 3단계 분석 접근법을 사용하여 비판적으로 검증합니다.

## 핵심 원칙
**양방향 편향 방지**: 모든 것을 공격하지도, 모든 것을 맹목적으로 받아들이지도 않습니다.
균형 잡힌 건설적인 분석을 위해 체계적인 3단계 접근법을 사용합니다.

## 1단계: 비판적 입장 (찾아내기)
**마음가짐**: "여기서 무엇이 잘못될 수 있을까?"
- [ ] 명백한 불일치점 식별
- [ ] 누락된 요소나 모순점 찾기
- [ ] 예상 패턴과의 편차 기록
- [ ] 아직 해결책 없이 잠재적인 문제 목록 작성

**결과**: 우려 사항 및 문제점의 원시 목록

**예시**:
- JSON 규칙에는 `npm run test:backend`가 있지만 `package.json`에는 해당 명령어가 없음
- 문서에서는 Biome을 주장하지만 일부 설정에는 ESLint가 보임
- 존재하지 않는 디렉토리 참조

## 2단계: 반비판적 입장 (옹호하기)
**마음가짐**: "이것이 실제로는 어떻게 옳을 수 있을까?"
- [ ] 문제가 계획된 미래 상태인지 고려
- [ ] 대안적인 해석 찾기
- [ ] 문제가 전환 단계인지 확인
- [ ] 원래 접근법을 뒷받침하는 증거 찾기

**결과**: 각 우려 사항에 대한 균형 잡힌 관점

**예시**:
- `test:backend`는 아직 구현되지 않은 계획된 명령어일 수 있음
- Biome/ESLint 혼합은 점진적인 마이그레이션 과정일 수 있음
- 누락된 디렉토리는 아키텍처 계획의 일부일 수 있음

## 3단계: 협력적 해결 (해결하기)
**마음가짐**: "가장 실용적인 해결책은 무엇인가?"
- [ ] 조사를 통해 실제 현재 상태 확인
- [ ] 수정해야 할 것과 실제로 올바른 것을 결정
- [ ] 상황을 개선하는 구체적인 조치 제안
- [ ] 비난이 아닌 건설적인 결과에 집중

**결과**: 실행 가능한 해결 계획

**조사 명령어 예시**:
```bash
# 실제 테스트 파일 위치 확인
find . -name "*.test.ts" -o -name "*.test.js" | head -10

# package.json 명령어 확인
grep -A5 -B5 "test:" package.json

# 실제 디렉토리 구조 확인
ls -la caret-src/ 2>/dev/null || echo "디렉토리가 아직 존재하지 않습니다"
```

## 검증 주기 적용

### 문서 불일치 시:
1.  **비판**: "이 문서들은 서로 모순된다"
2.  **반론**: "아마도 다른 시나리오를 다루고 있을 것이다"
3.  **해결**: 실제 사용 사례를 확인하고 조화롭게 만듦

### 기능 누락 시:
1.  **비판**: "기능 X가 문서화되어 있지만 존재하지 않는다"
2.  **반론**: "아마도 다음 구현을 위해 계획된 것일 수 있다"
3.  **해결**: 구현 상태를 확인하고 문서를 그에 맞게 업데이트

### 코드와 문서의 격차 시:
1.  **비판**: "코드가 문서와 일치하지 않는다"
2.  **반론**: "아마도 문서가 목표 상태를 보여주는 것일 수 있다"
3.  **해결**: 문서를 현재 현실에 맞게 조정하고, 미래 계획은 별도로 기록

## 성공 기준
- **균형 잡힌 분석**: 지나치게 가혹하지도, 맹목적으로 수용하지도 않음
- **증거 기반**: 모든 결론은 실제 조사에 의해 뒷받침됨
- **건설적인 결과**: 비판이 아닌 개선에 집중
- **명확한 실행 항목**: 불일치를 해결하기 위한 구체적인 단계
